# 報表公式與口徑

依目前 `03_sql_logic/views/` 與 `reports/` 核對，更新日期：2026-10-28。分頁與 SQL 對照見 [報表SQL說明](報表SQL說明.md)。

## 先分清楚四件事

- 交易量來源是 `v_rt_pr_hh24_clean.tx_cnt`，不是日總量表 `RT_CNT`。
- `AVG_TM` 來源單位為秒，view 乘以 1000 轉成毫秒；報表平均處理時間通常四捨五入成整數毫秒。
- 交易量峰日、處理時間峰日、CPU／Memory 最高時段是不同概念，不能互相代替。
- Pivot 只是把日期、月份或小時攤成橫向欄位，不是另外一套計算，也不是 Excel 可拖拉的樞紐分析表。

2026 年 9 月資料核對中，`RT_PR_HH24.CNT` 與 `RT_CNT.成功` 一致，而非 `RT_CNT.總筆數`；因此現行月報的交易量不能直接解讀為包含失敗、沖正等狀態的全部請求量。若要改成全部請求量，需先確認來源小時統計能否提供相同口徑，不能只替換月總量。

## 分類與排除條件

分類與名稱取自最新 `PR_CFG`：`PR_BZKIND` 是業務分類，`PR_TPKIND=1` 是交易類（update），`2` 是查詢類（query）。`FSAP` 只是其中一類，`ALL` 才是不篩選分類。

| SQL 系列 | FAC2FAS | 範圍與注意事項 |
| --- | --- | --- |
| `1` 至 `6.1` 的交易量報表、`7`／`7.1`／`7.2` | 排除 | 依本輪業務分類篩選；ALL 包含未分類交易 |
| `8`／`8.3` | 不排除 | 讀取 `v_monthly_transaction_stats`，比較完整月份 |
| `8.1`／`8.2` | 預設不排除 | SQL 的排除清單為空，可依程式的時間區間參數計算 |
| `1.1` 至 `1.1.4` | 監控不適用；找交易量峰值時排除 | 全平台主機資源，不依業務分類篩選 |

第 7、8 系列用內連接取得交易名稱與類別，沒有 PR_CFG 對照的交易不列出；但 ALL 的交易量分母可能仍包含這些交易。因此明細佔比加總不一定等於 100%。

最新分類快照會用於所有歷史月份，不是依報表月份選當時的快照。分類改動後重跑舊月報，分類數字與名稱也可能改變。

## 交易量與峰值

| SQL | 算法 |
| --- | --- |
| `1` | 月總量＝當月 `SUM(tx_cnt)`；峰日＝日總量最大日；峰時＝該峰日內小時總量最大時段 |
| `2`／`2.1` | 每日 `SUM(tx_cnt)`；2.1 將日期轉橫向 |
| `3`／`3.1` | 先找當月交易量峰日，再列該日各小時交易量；3.1 將小時轉橫向 |
| `4`／`4.1` | 每月總量；以 LAG 取得前一個有資料月份的總量，計算變化率 |
| `5`／`5.1` | 每月挑日總量最大日，並比較峰日交易量 |
| `6`／`6.1` | 每月先找交易量峰日，再找峰日內交易量最高小時，並比較峰時交易量 |

歷史系列的起月是比較基底，最後不顯示該起月；要顯示某月，起月應早於該月。沒有資料的月份不會自動補成零，LAG 的「前一月」實際是結果中前一個有資料月份。

目前不會自動阻擋資料不完整的月份；若前月只匯入月底一天，仍會拿該一天計算月增率，結果不能作為正式月比較。應先補齊前月及要比較的歷史期間，再重跑報表。

變化率＝`(本期值 - 前期值) / 前期值 × 100%`；分母為零時依 SQL 的 NULLIF 處理，不能當成 0% 成長。

`1` 至 `6.1` 並未全面指定峰值平手的次排序，不保證同量時永遠選同一天／小時。監控峰值系列 `1.1.2`、`1.1.3` 則明確取較早日期／小時。

## 處理時間與排行

對每個 PR_ID，先用小時資料計算每日交易量與每日平均：

```text
日交易量 = SUM(tx_cnt)
日平均毫秒 = SUM(avg_tm_ms × tx_cnt) / SUM(tx_cnt)
月／區間平均毫秒 = SUM(日平均毫秒 × 日交易量) / SUM(日交易量)
```

不能直接平均每小時或每日的平均時間。上述權重與非空資料須一致；缺失值並不會由程式自動補成有效監測值。

| 報表 | 峰日 | 峰時／峰值處理時間 |
| --- | --- | --- |
| `7`／`7.1`／`7.2` | 每日加權平均處理時間最高日 | 「峰值處理時間」是該日平均，不是單筆最慢交易，也不是峰時耗時 |
| `8`，以及 `8.3` 使用的 view | 同上；同值取較早日期 | 峰時取整月內該 PR_ID 交易量最多的小時，同量取較早日期與小時；不一定在處理時間峰日 |
| `8.1` | 每個比較期間內的交易量最高日 | 峰值處理時間是該交易量峰日的日平均；峰時取整段期間，不限峰日，平手未完整固定 |

`7.1` 只列 update 的 Top 6，`7.2` 只列 query 的 Top 6；它們的佔比分母不是 Top 6 加總，也不是 update／query 各自的總量。

## 佔比與月度比較

- `ALL`：佔比分母是該報表範圍的全系統總量，須留意上方 FAC2FAS 排除差異。
- 分類報表：分母是該分類在該報表月份或期間的總量。`8`／`8.3` 改用 view 的「分類內佔比」，輸出仍叫「交易量佔比」。
- `8` 是完整目標月，**不使用** `rangeStartTime`／`rangeEndTime`。
- `8.1`／`8.2` 才使用自訂本期時間；前期始終是 targetMonth 的完整前一月，不是自訂本期等長往前平移。
- `8.3` 使用前一個完整月與目標完整月。`8.1`／`8.2`／`8.3` 都以內連接配對，只列兩期皆存在的交易，不會自動列出新增／消失的交易。
- 「實際交易天數」是來源日聚合有列的日期數，不是自動填滿的日曆天數，也不是一律只算交易量大於零的日數。

## CPU 與 Memory

來源是 MON_LOG 的 SERVER 監控，經 daily／hourly views 彙整，並用 Eureka 參考資料對應 `FSAP-RUNTIME`。不是 JVM heap，也不能只由交易量推算。

| 站點 | SQL 中固定的主機 |
| --- | --- |
| 主地 | `10.4.240.183`、`184`、`185`、`186`，4 台 |
| 異地 | `10.4.240.187`、`188`，2 台 |

每台先對實際取樣計算平均／最大，再按下表彙整站點。缺少的主機、日期或取樣不會補成零，分母會隨實際非空資料變動；應先確認資料完整度。

| SQL | 平均欄 | 最大欄 |
| --- | --- | --- |
| `1.1` | 站點內各主機各日平均值再平均 | 無 |
| `1.1.1` | 每日各主機平均值再平均 | `_max` 是各主機當日最大值再平均，**不是**站點最高單筆值 |
| `1.1.2` | 峰日全日或峰時各主機平均值再平均 | 任一主機在該時段的最高取樣值 |
| `1.1.3`／`1.1.4` | 每小時各主機平均值再平均 | 任一主機在該小時的最高取樣值 |

`1.1.2` 輸出峰日／峰時各一組平均、最大，共 4 列；`1.1.3` 固定列出峰日 24 小時；`1.1.4` 只列監控資料實際存在的日期小時，不保證整月每小時都有列。

`1.1.2` 至 `1.1.4` 的站點彙整以百分之一為單位做整數平均與平手進位，但上游 daily／hourly views 仍先使用浮點 AVG 與 ROUND，因此不能保證全流程符合十進位平手進位；`1.1`／`1.1.1` 也使用浮點運算。2026-09-30 10 時異地 CPU 曾出現 SQL 為 2.67%、逐台十進位平手進位重算為 2.68% 的 0.01 個百分點差異，非取樣缺漏。

資料檔通常在隔日包含前一天資料。月報應核對次月首日來源檔是否已匯入；檔名日期不等於每一列的交易日／監控日。CPU、Memory 的最高時間也不必等於交易量峰時。

## 核對順序

1. 確認 JAR、SQL、外部分頁清單與分類快照版本。
2. 查看 `report-params.json`、分類摘要、`failure=0`，再核對來源是否缺日。
3. 對照 `SUM/` 或分類目錄的原始 CSV，再查看根目錄正式月報選入的分頁。
4. 不要把缺資料造成的空表或 Message 頁當成零交易、零使用率。
