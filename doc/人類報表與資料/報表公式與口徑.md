### 3.2 公式

#### 月交易總量

先依日期彙總全系統日交易量：

```text

```

再加總整個月份：

```text
月交易總量 = SUM(FSAP_Daily(d))
```

#### 峰日

```text
峰日 = argmax_d FSAP_Daily(d)
峰日交易量 = max_d FSAP_Daily(d)
```

SQL 實作方式：

- 先做 `GROUP BY tx_dt_str`
- 再 `ORDER BY 日交易量 DESC LIMIT 1`

#### 峰時

限定在「峰日」那一天，再依小時彙總：

```text
PeakHour(h) = SUM(tx_cnt on peak day)
峰時 = argmax_h PeakHour(h)
峰時交易量 = max_h PeakHour(h)
```

### 3.3 補充

這支報表目前的峰日判定仍使用 `v_rt_pr_hh24_clean` 的小時資料加總，不是 `v_rt_cnt_clean`。

位置：

- [7.2.交易量統計-TOP6查詢類.sql](/Users/sonic711/Desktop/development/fsap-monitor-util/fsap-month-report-develop/03_sql_logic/reports/7.2.交易量統計-TOP6查詢類.sql)

### 9.1 用到的來源

- 交易量：`v_rt_pr_hh24_clean`
- 平均處理時間：`v_rt_pr_hh24_clean`
- 類別與名稱：`v_pr_info`

### 9.2 BaseDaily 的定義

對每個 `PR_ID`、每一天，先建立：

```text
DailyCnt(p, d) = SUM(tx_cnt)
DailyAvgMs(p, d) =
  SUM(avg_tm_ms(p, d, h) * tx_cnt(p, d, h))
  / SUM(tx_cnt(p, d, h))
```

也就是：

- `daily_cnt` 來自 `v_rt_pr_hh24_clean.tx_cnt` 的日加總
- `daily_avg_ms` 來自 `v_rt_pr_hh24_clean.avg_tm_ms` 依小時交易量 `tx_cnt` 加權

### 9.3 全系統總交易量

```text
AllSysTotal = SUM(DailyCnt(p, d))
```

注意：

- 這個分母只排除 `FAC2FAS`
- 但不再區分 `update` / `query`

也就是 `7.1` 和 `7.2` 的 `交易量佔比` 分母，都是**整個系統總量**

### 9.4 單一交易類型的交易總量

```text
SysTotal(p) = SUM(DailyCnt(p, d))
```

### 9.5 平均處理時間

這裡不是簡單平均，而是**以交易量做加權平均**：

```text
SysAvgMs(p) =
  SUM(DailyAvgMs(p, d) * DailyCnt(p, d))
  / SUM(DailyCnt(p, d))
```

這是目前 `7 / 7.1 / 7.2` 最重要的公式之一。

意思是：

- 某一天交易量越大，那一天的平均處理時間對整月平均影響越大

### 9.6 峰值處理時間欄位的真實公式

這是最容易誤解的地方。

SQL 現在的寫法是找：

```text
PeakProcessDay(p) = argmax_d DailyAvgMs(p, d)
```

然後取那一天的日期與處理時間：

```text
PeakProcessAvgMs(p) = DailyAvgMs(p, PeakProcessDay(p))
```

所以目前欄位 `峰值處理時間` 的真實意義是：

```text
每日平均處理時間最高那一天的平均處理時間
```

不是：

- 峰時的處理時間
- 單筆交易的最大處理時間

### 9.7 為什麼峰值處理時間通常會大於或等於平均處理時間

因為目前比較的是：

```text
整月加權平均處理時間
vs
每日平均處理時間最大值
```

在同一批 `DailyAvgMs` 與正交易量權重下，最大值理論上不會小於加權平均：

```text
max(DailyAvgMs) >= weighted_avg(DailyAvgMs)
```

如果報表出現相反結果，優先檢查是否使用了舊版產出、不同 SQL 版本，或來源資料 / join 條件不一致。

### 9.8 欄位名稱的語意風險

因此目前 `峰值處理時間` 代表的是「處理時間最高日」的日平均，不是單筆最大處理時間。

若要避免誤解，較精確的名稱可以是：

- `最高日平均處理時間`
- 或 `處理時間峰日`

### 10.2 和 `7` 系列最大的差異

### 10.3 每日交易量

```text
DailyCnt(p, d) = SUM(tx_cnt)
```

### 10.4 每日平均處理時間

因為底層是小時表，所以先在「日」層級做一次加權平均：

```text
DailyAvgMs(p, d) =
  SUM(avg_tm_ms(p, d, h) * tx_cnt(p, d, h))
  / SUM(tx_cnt(p, d, h))
```

### 10.5 區間平均處理時間

接著再從日層級做一次區間加權平均：

```text
SysAvgMs(p) =
  SUM(DailyAvgMs(p, d) * DailyCnt(p, d))
  / SUM(DailyCnt(p, d))
```

### 10.6 峰日

```text
PeakProcessDay(p) = argmax_d DailyAvgMs(p, d)
PeakProcessDayVolume(p) = DailyCnt(p, PeakProcessDay(p))
```

第 8 頁目前已和第 7 頁一致，`峰日` 欄位代表「處理時間峰日」，不是交易量峰日。

### 10.7 峰時

這裡不是在峰日內找峰時，而是在整個區間內直接找該 `PR_ID` 的最大 `tx_cnt`：

```text
PeakHourVolume(p) = max(tx_cnt over all day-hour rows in range)
PeakHourDate/Hour(p) =
  first row by tx_cnt DESC, tx_dt_str ASC, tx_hour ASC
```

也就是：

- `峰日` 與 `峰時` 的挑選範圍其實不完全一樣
- `峰日` 來自日聚合
- `峰時` 來自整段區間的 hourly raw rows
- 若多個小時交易量同為最大值，固定取較早日期、較早小時，避免 `arg_max` 在同值時挑到不同結果

### 10.8 峰值處理時間

和 `7` 系列一樣，目前輸出的：

```text
峰值處理時間 = 處理時間峰日的日平均處理時間
```

而不是峰時處理時間。

### 10.9 實際交易天數

```text
TxDaysCnt(p) = COUNT(tx_dt_str)
```

因為 `BaseDaily` 已經先 `GROUP BY PR_ID, tx_dt_str`，所以這裡的 `COUNT(tx_dt_str)` 實際上是：

```text
有發生交易的日期筆數
```

也就是「實際交易天數」。

## 11. `8.1` / `8.2` / `8.3` 月度比較

### 11.1 `8.1` 詳細比較

`8.1` 分別以 `${previousRangeStartTime}` / `${previousRangeEndTime}` 與 `${rangeStartTime}` / `${rangeEndTime}` 從 `v_rt_pr_hh24_clean` 建立前一月與本月的每日統計。它會輸出交易總量、佔比、峰日、峰時、加權平均處理時間、峰值處理時間與實際交易天數，再計算交易量變化與變化率。

兩月資料以 `PR_ID` 做內連接，因此只會列出兩個期間皆有資料且可在 `v_pr_info` 找到名稱的交易類型。峰日依每日交易量最高日判定；峰值處理時間是該峰日的每日加權平均處理時間。

### 11.2 `8.2` 簡易比較

`8.2` 使用相同的兩段時間與資料來源，但只輸出交易名稱、前一月與本月的筆數及佔比、筆數變化與變化率。它同樣只列出兩期間皆存在的 `PR_ID`。

### 11.3 `8.3` MOM 比較

`8.3` 不直接掃描小時明細，而是讀取 `v_monthly_transaction_stats`，以 `${previousTargetMonth}` 與 `${targetMonth}` 比較兩個完整月份。前一月與本月以交易類型內連接，故同樣只列出兩月都有資料的項目。

## 12. 目前最容易被誤解的公式清單

### 12.1 `7 / 7.1 / 7.2 / 8` 的 `峰值處理時間`

目前實際公式：

```text
峰值處理時間 = max_d DailyAvgMs(p, d)
```

不是：

```text
峰時處理時間或單筆最大處理時間
```

### 12.2 `7 / 7.1 / 7.2` 的 `平均處理時間`

目前實際公式：

```text
整月加權平均
```

不是簡單日平均：

```text
AVG(每日平均處理時間)
```

### 12.3 `7 / 7.1 / 7.2` 的 `交易量佔比`

目前實際公式：

```text
某 PR 交易總量 / 全系統總量
```

分母不是：

- 同類別總量
- Top 6 總量

而是整個系統的總交易量。
