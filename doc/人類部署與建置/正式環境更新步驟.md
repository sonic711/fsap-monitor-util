# 正式環境更新步驟

適用於分類月報與 CPU／Memory 報表改版，包含新版 `SUM/` 與跨分類正式月報輸出結構。以下路徑沿用專案 Jenkinsfile；正式環境若不同，請替換成實際位置。

這次必須一起更新 **JAR、外部 SQL、PR_CFG 分類快照**。目前 Jenkins 只在正式主機執行既有 JAR，不負責部署；push 不代表正式環境已更新。程式已包含本次改動，不必再套附件 patch。

## 1. 在建置電腦打包

確認使用本次新版原始碼，在專案根目錄執行：

```bash
./gradlew clean test bootJar
```

離線建置沿用 [Gradle離線建置](Gradle離線建置.md) 的倉庫與 `--offline` 設定。打包成功後，準備以下三項：

| 要帶到正式主機的檔案 | 原始碼內位置 |
| --- | --- |
| 新 JAR | `build/libs/fsap-monitor-util-0.1.0-SNAPSHOT.jar` |
| 整份 SQL 目錄 | `fsap-month-report-develop/03_sql_logic/` |
| 分類快照 | `fsap-month-report-develop/02_source_lake/PR_CFG/PR_CFG-20261022.jsonl.gz` |

**本次特別注意：上述快照本機有，但目前沒有被 Git 追蹤，不能只靠 git pull 取得。** 請另外攜帶這個檔案；已核對它包含 128 筆有效分類資料。若建置電腦沒有此檔，可由交付的完整修改後程式碼 ZIP 取得。

## 2. 暫停正式環境與備份

暫停每日產報、月報上傳兩個 Jenkins Job，等待執行中的工作結束；若有 Web 服務也先停止，避免資料庫同時被使用。

在停止後，備份舊 JAR、`config/`，以及 `fsap-month-report-develop/` 下的 `03_sql_logic/`、`05_database/`、既有 `02_source_lake/PR_CFG/`（若有）。其他資料目錄保持原樣。

## 3. 放入新版三項檔案

| 新版內容 | 正式主機位置 |
| --- | --- |
| JAR | `/app/fsap-monitor-util/fsap-monitor-util-0.1.0-SNAPSHOT.jar` |
| SQL | `/app/fsap-monitor-util/fsap-month-report-develop/03_sql_logic/` |
| 分類快照 | `/app/fsap-monitor-util/fsap-month-report-develop/02_source_lake/PR_CFG/PR_CFG-20261022.jsonl.gz` |

SQL 請將舊目錄移到專案資料目錄以外備份，再放入整份新版，避免留下已移除的 `views/v_pr_info.sql`。分類快照只新增這個檔案，不要替換整個 `02_source_lake/`；已有同名檔時先核對內容，不要直接覆蓋。

**保留正式環境原有的 `config/application.yml`、`00_info/`、歷史 Excel、數據湖、既有報表與資料庫，不要用開發電腦的整個資料目錄覆蓋。** 不需刪除 DB，也不需重匯全部歷史資料。

確認 Jenkins 的 `TARGET_HOST` 是剛更新的主機，Console 中 `java -jar` 的路徑也是上述 JAR。正式主機可用 `sha256sum /app/fsap-monitor-util/fsap-monitor-util-0.1.0-SNAPSHOT.jar` 計算 SHA-256，與建置電腦準備上傳的 JAR 比對；Mac 可用 `shasum -a 256 build/libs/fsap-monitor-util-0.1.0-SNAPSHOT.jar`。兩邊應完全相同。

## 4. 確認設定與分類資料

正式環境的 `config/application.yml` 若有設定 `fsap.ingest.target-sheets`，請保留原清單並加入 `PR_CFG`；沒有這項設定則使用新版內建值，不必新增。使用新版預設六種分類（含 FSAP）時，不必另加 `fsap.report`。

若外部設定仍有舊的分類清單，請在既有 `fsap.report` 下更新以下兩項，其他設定保留；只改產報清單，仍可能讓比較活頁簿漏掉 FSAP：

```yaml
fsap:
  report:
    target-bzkinds: [NCL, NCB, BIS, FAC, NIS, FSAP]
    combined-workbook:
      bzkinds: [NCL, NCB, BIS, FAC, NIS, FSAP]
```

同時更新外部 `reports/1.交易量統計-當月.sql`，「系統」欄才會隨分類顯示，不再固定顯示 FSAP。總覽顯示「全系統（ALL）」，FSAP 分類則顯示「FSAP」。這兩份外部清單與 SQL 的修正不需要重新打包 JAR，但既有 JAR 必須已支援分類參數。

**新的 SUM 目錄與正式月報改名需要部署新版 JAR。** 若外部另有 `combined-workbook.all-sheets`／`reports`，請依 [啟動與產生報表](../人類操作/啟動與產生報表.md#依業務分類產出) 更新整份分頁清單，讓四種日期／峰值分頁改用 Pivot，並加入歷史峰日與歷史峰日峰時；舊 `filename` 設定可移除。

分類對照會採日期最新的 `PR_CFG`，不一定是剛複製的 20261022。若正式環境已有更新快照，該份快照的每筆 `PR_TPKIND` 都必須是 1 或 2，否則產報會中止。

## 5. 在正式主機手動驗證

以原服務帳號執行下列指令；函式 `fsap` 只是這次 Shell 的指令簡寫。確認要試產的月份，以下以 2026 年 9 月為例：

```bash
cd /app/fsap-monitor-util
mkdir -p /app/fsap-monitor-util/tmp
fsap() {
  /app/java/java17/bin/java \
    -Djava.io.tmpdir=/app/fsap-monitor-util/tmp \
    -jar /app/fsap-monitor-util/fsap-monitor-util-0.1.0-SNAPSHOT.jar \
    --fsap.paths.base-dir=/app/fsap-monitor-util/fsap-month-report-develop "$@"
}
fsap generate-report --help
fsap doctor
fsap sync-views
fsap generate-report --target-month 2026-09
```

先確認 help 中有 `--target-bzkinds`；沒有時表示該 JAR 尚未包含分類功能，應先確認版本與部署位置。每一步成功才執行下一步。檢查 `failure=0`、`[分類摘要]` 與 `Notice`，並在新的 `04_report_output/<執行時間>/` 確認：根目錄的跨分類正式月報、`SUM/` 內的 ALL CSV 與完整彙總 Excel、各分類子目錄，以及 SUM 彙總中的 `1.1.2` 至 `1.1.4` 新監控分頁。不應建立 `REPORT/`；預設六種分類都成功產出時，正式月報為 55 頁。分類不在快照內會略過，需核對是否符合預期。試產不會自動上傳 SFTP，舊批次不會自動搬移。

若需要更新實際分類，先將含 `PR_CFG`、`PR_TPKIND` 的每日 Excel 放到 `01_excel_input/`，執行 `fsap ingest --date YYYYMMDD` 後再驗證。若最新快照的分類欄位錯誤，修正對應日期的來源 Excel，再用 `fsap ingest --date YYYYMMDD --force` 重建該日；只補較舊快照不會取代錯誤的最新資料。

## 6. 恢復服務與排程

驗證成功後，以原方式啟動 Web（若有），恢復兩個 Jenkins Job，保持執行時間錯開。此次分類改版不要求修改原排程。

`Jenkinsfile.upload` 會上傳根目錄的新跨分類正式月報，不會自動上傳 `SUM/` 或分類子目錄；不需為新目錄結構修改上傳指令。另外，倉庫的上傳 Job 尚未帶 `-Djava.io.tmpdir`；正式主機若沿用先前的 `/tmp` 限制，請確認該 Job 也和每日 Job 一樣指定 `/app/fsap-monitor-util/tmp`。

若驗證失敗，先不要恢復排程；停止相關程式後，還原備份的 JAR、SQL、設定、資料庫與原 PR_CFG，再以原方式啟動。

## 遇到 targetBzkind 參數錯誤

`Unknown or unresolved report parameter: targetBzkind` 表示 SQL 已使用新參數，但執行中的程式未提供它。新版程式會自動傳入 `ALL` 或各分類代碼，不需要在外部設定補上 `targetBzkind`。

先核對 Jenkins 的目標主機、JAR 路徑，再依上方 help 與 SHA-256 檢查版本。不一致時，重新用新版原始碼 `clean test bootJar` 並部署正確 JAR。若版本完全相同仍出錯，請保留該次 Jenkins Console 的完整啟動指令與錯誤前後紀錄繼續排查；不要先把 SQL 的分類參數寫死成 ALL。
