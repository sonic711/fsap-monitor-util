# 正式環境更新步驟

以下沿用 Jenkins 的 `/app/fsap-monitor-util` 路徑。**push 不會部署**；兩份 Pipeline 都只執行正式主機既有 JAR。

## 1. 打包並準備交付

在新版原始碼根目錄使用 JDK 17：

```bash
./gradlew clean test bootJar
```

離線環境依 [Gradle離線建置](Gradle離線建置.md) 加上倉庫與 offline 設定。

| 交付內容 | 位置／用途 |
| --- | --- |
| 新 JAR | `build/libs/fsap-monitor-util-0.1.0-SNAPSHOT.jar` |
| 新 SQL | 整份 `fsap-month-report-develop/03_sql_logic/` |
| 外部設定 | 必須帶入新版匯入與報表規則，與正式環境原有 `config/application.yml` 合併，保留連線與路徑，不可整份用開發設定覆蓋 |
| 分類與來源資料 | 首次部署或更正分類時準備 PR_CFG 與必要來源，不要假設 Git 會帶入 |
| 監控配置 | 使用監控匯出時帶入 `config/monitor-data.json` |

Git 不收錄數據湖。既有交付可能另附 `PR_CFG-20261022.jsonl.gz`，但新 clone 不會取得；優先匯入帶有效 PR_CFG 的每日 Excel，或從可信的舊交付取回快照。不要把開發電腦整份數據湖覆蓋正式資料。

## 2. 停止存取並備份

暫停每日產報與每月上傳 Job，等待執行結束；若 Web 使用相同 DB，也先停止。

備份舊 JAR、config 與資料根目錄中的 `00_info/`、`02_source_lake/`、`03_sql_logic/`、`05_database/`。原始 Excel 與既有報表依既定保存政策保留。DB 單檔不足以還原所有報表資料。

## 3. 更新正式主機

1. 將新 JAR 放到 `/app/fsap-monitor-util/fsap-monitor-util-0.1.0-SNAPSHOT.jar`。
2. 將舊 SQL 移到資料根目錄以外備份，再放入完整新版 `03_sql_logic/`，避免舊 view 殘留。
3. 合併外部設定；必要時新增或匯入 PR_CFG，不替換整個來源目錄。
4. 同步每日 Job 的 Jenkinsfile 與月報 Job 的 Jenkinsfile.upload，尤其是手動貼上的 Pipeline。

本次 JAR 與外部設定須一併更新：業務設定不再包進 JAR，ALL 原始成品在 SUM，跨分類正式月報在批次根目錄。範本見 [config/application.yml](../../config/application.yml) 的 `fsap.report`，分工見 [設定檔分工與覆寫](../人類操作/設定檔分工與覆寫.md)：

- 六個分類清單含 FSAP；外部 `target-bzkinds` 與 `combined-workbook.bzkinds` 都要符合預期。
- `target-bzkinds`、`all-sheets`、`reports` 三份清單須明確提供；缺少時產報中止，不再採內建清單。明確空清單仍可停用分類或比較。
- 當月每日／峰日峰時／歷史峰日／歷史峰日峰時採 2.1、3.1、5.1、6.1 Pivot。
- 移除不再使用的 `combined-workbook.filename`；保留 remote 等正式連線設定。

兩台主機可比對 JAR 的 SHA-256：正式 Linux 用 `sha256sum 檔案`，Mac 用 `shasum -a 256 檔案`。另確認 Jenkins TARGET_HOST、JAR 路徑與外部設定路徑。

## 4. 試產並核對

使用 [啟動與產生報表](../人類操作/啟動與產生報表.md#1-確認資料與設定) 的 fsap 函式，明確讀取正式外部設定，並執行：

```bash
fsap doctor
fsap sync-views
fsap generate-report --target-month 2026-10
```

月份改成要驗證的月份。`doctor` 不檢查資料完整度；若缺檔先 ingest。以新的執行時間試產，不重用舊時間。

確認 `failure=0`、分類摘要與 Notice；SUM 中有全部 CSV／原始彙總，各分類仍有成品，根目錄正式月報為 `維運月度報表_MM月彙總_<執行時間>.xlsx`。預設六類全部產出時共 55 頁；監控 1.1 系列仍在 SUM／分類的完整彙總內，不在預設正式月報。

產報不會自動上傳。需要上傳驗證時先確認目的地、同名檔與是否允許覆蓋，再依 [SFTP下載與上傳](../人類操作/SFTP下載與上傳.md) 操作。未連線測試不能證明正式 SFTP 帳號有寫入權限。

## 5. 恢復排程

確認成功後恢復 Web 與兩個 Job。月報 Job 會重新產報再上傳根目錄正式月報，不會補匯入資料；與每日 Job 錯開。

兩份 Pipeline 已建立 `/app/fsap-monitor-util/tmp` 並使用 java.io.tmpdir，仍須確認帳號權限及掛載點允許 DuckDB 原生函式庫載入。舊批次不會自動搬成新結構。

驗證失敗先保持停機，還原備份的 JAR、SQL、設定與受影響資料；正常關閉所有 DB 存取後才替換 DB。

## 常見版本／分類問題

- `Unknown or unresolved report parameter: targetBzkind`：核對實際啟動的 JAR 與外部 SQL 是否同版；不用在設定檔補同名參數，也不要寫死 ALL。
- 新快照缺 PR_TPKIND：修正對應日期 Excel，執行 `ingest --date YYYYMMDD --force`，再同步、產報。較舊快照不會取代日期較新的錯誤快照。
- SFTP 的 remote.url 未讀到：核對外部設定及指令位置，不能因 Excel 檔名正常就判定連線配置正確。
