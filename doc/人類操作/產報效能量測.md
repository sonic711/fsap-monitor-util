# 產報效能量測

量測日期：2026-10-28。這次只調整執行方式，不修改 SQL、分類、排除條件或分頁清單。

## 修改前後結果

修改前以 `7a2fac3` 的程式為基準。兩版本都使用同一份 9 月測試資料、PR_CFG 20261022、外部設定、SQL 與初始 DB 副本；每次啟動新的 Java 程序，單次只執行一批報表。

| 次數 | 修改前（秒） | 修改後（秒） |
| --- | ---: | ---: |
| 1 | 13.232 | 4.444 |
| 2 | 13.204 | 4.313 |
| 3 | 13.151 | 4.657 |
| 4 | 12.590 | 4.112 |
| 5 | 12.182 | 4.096 |
| 中位數 | **13.151** | **4.313** |
| 平均 | 12.872 | 4.324 |

中位數縮短 **67.2%**，約為原來的 **3.05 倍速度**，每批少約 **8.84 秒**。即使以新版最慢的 4.657 秒對比舊版最快的 12.182 秒，仍有明確改善。

量測範圍是 `ReportGenerationService.generate()`，包含 DB 連線、macros／views 同步、分類檢查、全部 SQL、CSV、Excel 與正式月報，不含 Spring 啟動、Excel 匯入及 SFTP。

測試條件：

- Java 17.0.12、DuckDB JDBC 1.5.2.0、`-Xmx2g`，相同電腦、單批依序執行。
- 31 份來源 Excel 已事先匯入；月報月份固定 2026-09，ALL 加七個分類，每次 184 個報表結果、66 頁正式月報、零失敗。
- 先測舊版三次、新版三次，再以「舊、新、新、舊」交錯補測；量測期間不並行建置或執行其他報表。
- 每次從相同 DB 副本開始，使用不同輸出目錄；不清除作業系統檔案快取，這不是磁碟冷啟動測試。
- 這是目前測試資料的實測值，不保證不同主機或多年資料一定有相同比例。

## 為什麼變快

原本每支 SQL 都會透過 views 反覆讀取、解壓 JSONL.GZ 並重新聚合，多個分類又重做相同工作。這次在同步 views 後，先將下列五個 view 的結果建立成本連線的暫存表，供整批報表重用：

- `v_cfg_pr_bzkind`
- `v_rt_pr_hh24_clean`
- `v_monthly_transaction_stats`
- `v_prod_monitor_daily_count`
- `v_prod_monitor_hourly_count`

只處理存在的白名單 view，不處理其他 view，也不替換同名永久 table。這五個結果會包含其原有完整資料範圍，不會為了加速而刪去歷史月份、少跑 SQL 或少產分頁。

暫存僅在本次產報連線中有效，連線關閉便清除；下次會重新建立，不會沿用上一次的分類或交易資料。原始數據湖、永久 view 定義與報表 SQL 不因暫存而改寫；原有的 `sync-views` 流程仍會正常更新永久 views。

## 內容驗證

十批產物共核對 1,840 份 CSV、90 份 Excel、2,500 個分頁，檢查交易代號、數量、分類、處理時間、排行、峰值與來源資料的對應，以及每個 Excel 分頁和該批 CSV 的一致性；Excel 樣式也未改動。

不能宣稱所有檔案逐位元相同。舊版自身重跑已有兩種不穩定結果：

- `1.1.1` 每日監控在浮點邊界有 0.01 個百分點差異；另依原始取樣進行 19,200 個十進位數值核對，差異均未超過 0.01 個百分點。
- SQL 未指定完整平手次排序時，可能選到不同但同樣符合峰值條件的日期／小時，或交換同量交易的順序。核對時會驗證被選值確實符合原始資料的最大值、日期對應處理時間及排序條件，不直接忽略這些欄位。

上述既有差異已單獨記錄，未發現其他非預期差異。這次沒有順便更改四捨五入或平手規則，也沒有修正缺少 8 月完整資料造成的月增比較限制。

## 部署與回復

需要重新打包並部署 JAR，僅更新外部設定不會套用這次 Java 優化。CLI 與 Web 共用相同產報程式；Web 部署後需重啟。

預設開啟 `fsap.report.materialize-views=true`，穩定預設放在 JAR 內。要回到原本逐查詢讀取 views 的路徑，可在外部設定加上：

```yaml
fsap:
  report:
    materialize-views: false
```

這只是新增一個鍵，既有的分類與分頁清單仍須保留。也可用命令列的 `--fsap.report.materialize-views=false` 暫時覆寫，放在 `generate-report` 前。

成功產報後，`logs/report_execution.log` 會記錄產報總耗時；開啟時另記錄暫存的 view 數及建立耗時。總耗時包含建立暫存及輸出檔案，不只是 SQL 時間。

暫存會使用額外的 DuckDB 記憶體／暫存空間，多年資料應在部署主機再量測。這不允許 ingest、Jenkins 或 Web 同時改動同一份來源，也不是對所有外部檔案的一次原子快照。

## 自行重測

使用獨立測試資料目錄，不要直接在正式目錄量測。固定資料、設定、SQL、Java 與月份，不要同時匯入資料；每次用新的批次時間，避免覆寫舊產物。

以下兩次只切換暫存開關，查看執行紀錄中的「產報總耗時」；建議交錯各跑至少五次，再比較中位數及結果內容：

```bash
java -Xmx2g -jar build/libs/fsap-monitor-util-0.1.0-SNAPSHOT.jar \
  --fsap.paths.base-dir=/path/to/benchmark-data \
  --fsap.report.materialize-views=false \
  generate-report --target-month 2026-09 --timestamp 202610281901

java -Xmx2g -jar build/libs/fsap-monitor-util-0.1.0-SNAPSHOT.jar \
  --fsap.paths.base-dir=/path/to/benchmark-data \
  --fsap.report.materialize-views=true \
  generate-report --target-month 2026-09 --timestamp 202610281902
```

本次原始量測與比對證據保存在專案的 `build/report-performance/`，包含新舊 JAR、各次 JSON／log、`input-manifest.json`、`timing-summary.json`、`semantic-comparison.json` 及全部產物。這些檔案不納入 Git，執行 `clean` 會刪除；上表則保留本次結果供審閱。
